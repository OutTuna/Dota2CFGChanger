# Update trust model and release requirements

The standalone updater trusts **GitHub's authenticated HTTPS distribution for
OutTuna/Dota2CFGChanger**. It requires the repository's fixed `latest` asset URLs,
validates a stable release and asset size, checks SHA-256 after downloading and
again before installation, and verifies startup before removing the old executable.
API redirects are refused. Asset redirects must remain HTTPS, with certificate
verification enabled and a finite redirect limit. API and download sizes are bounded.
Local downloads use a workspace reserved with exclusive directory creation; cached
assets and update paths cannot be symlinks/reparse points at the checked components.

SHA-256 is **integrity verification, not an independent signature of the author**.
The digest and executable originate from the same GitHub release. This does not
protect against a compromised repository, release token, release workflow, trusted
TLS interception endpoint or GitHub itself. Same-user malware is not isolated by
application directory checks. No source code audit can establish the authenticity
of a future release whose publishing authority is compromised.

## Independent author authentication (release gate if required)

No signing key or signing certificate was supplied for this audit. A production
key must belong to the maintainer, not be silently generated by an auditing agent
or committed with the sources. Adding a verifier with a placeholder key would not
protect existing installations.

The smallest extension for an independent trust anchor is a signed manifest:

1. The maintainer creates an offline signing key, selects its backup and rotation
   policy, and supplies only the public verification key for the application.
2. Sign an exact, canonical manifest containing format version, release version,
   immutable release/commit identity, platform, asset name, length and SHA-256.
   Verify the signature **before accepting any of those fields for installation**.
3. Store the private signing key outside the release-upload authority. Signing in
   the same workflow with the same compromised permissions does not establish the
   desired separation. An offline signing step or separately approved signing job
   can fit this small project's release process.
4. Ship the signature and manifest with an immutable versioned release. Pin the
   public key in the verifier. Reject missing/invalid signatures in the protected
   update channel; do not silently fall back to unsigned installation.
5. Test forged signatures, changes to each signed field, platform/filename swaps,
   rollback attempts, key rotation and interrupted installation on Windows/Linux.
   Define how older unsigned clients migrate to the signed update channel.

The current mutable `latest` tag is also not an anti-rollback authority. Version
comparison prevents normal downgrade offers relative to the running version, but
there is no independent, persisted highest trusted release counter.

No signing infrastructure, release credentials, version changes or publications
were introduced by this audit. The existing update feature remains available
under the explicit GitHub trust model above. Native HTTPS/redirect integration,
filesystem crash recovery and independent signature deployment remain release
validation work, not claims inferred from the mocked network unit tests.
